# 红果播放器技术路线与复盘

本文件记录本次红果播放器开发的路线演进、取舍与经验，范围为 1.0.x 交付阶段。开发时应遵守 [AGENTS.md](../AGENTS.md) 的现行规范；逐次任务、失败及验证证据见 [TASKS.md](../TASKS.md)，操作入口见 [CLI 文档](cli.md)。本文件不替代开发规范，也不将阶段性实测外推为全部能力。

## 技术路线演进

| 路线 | 本项目实测与取舍 | 经验与验证边界 |
| --- | --- | --- |
| 官网搜索、扫码与浏览器验证 | 先确认身份恢复、可用目录与实际播放，建立可工作的基线 | 登录成功不代表任意剧集、任意清晰度有权播放 |
| WebView2 官方播放器 | 已验证代表集播放、切集、跳转与视频层透明，随后因原生交互需求转为兼容基线 | 子 HWND 的布局、鼠标、截图和透明合成须单独处理，不能用无界面浏览器结果替代嵌入验收 |
| libmpv 隔离原型 | 原始 CENC 分轨输入出现花屏，内部截图与 WGC 均确认；低负载数据不作为优势 | 这是所测输入未适配，不能据此判定 libmpv 引擎不适用；未完成同一兼容输入下的最终性能比较 |
| Iced/GStreamer 原生 360p | actual currentSrc 的完整音视频兼容流可正确解码，验证原生纹理与透明 | 360p 是该网页兼容输入的实际档位，不能推断为播放器分辨率上限 |
| 官网 720p 双轨适配 | 内存处理已验证的 CENC 音视频轨并交给同一 playbin，代表集画面、音频时间及跳转通过 | 整集准备和浏览器取源仍有等待成本；网页目录与可播放后续集并不等价，不能用预加载掩盖根因 |
| App 目录与有界 Range 输入 | 标准 GstProtectionMeta 路径在所测输入未通过后，采用样本索引适配；代表性中后段 720p、远距跳转及首次读取量通过 | 保留已验收 Iced/GStreamer 与控件，只更换取源/适配层；Windows 当前默认，不先下载整集，不静默回退网页或低清 |

## 最终采用的链路

当前主链：`系统安全凭据 → 身份核对 → 固定源码 Go App 适配器 → Python 有界 Range/CENC 处理 → GStreamer playbin 音视频解码 → Iced GPU 纹理/独立控件`。账号与媒体辅助通过匿名管道交接，媒体服务仅绑定带不可猜令牌的本机回环资源；实际播放不需要浏览器持续取源。`native-player-prototype` feature 名仅为兼容既有命令，Windows 已默认启用；这不是已证实的零拷贝方案，macOS 不据此宣称功能对等。

源码职责分开：`src/desktop/pages.rs` 负责页面与控件，`account.rs` 负责账号桥接，`native_player.rs` 负责播放器状态及管线；`scripts/hongguo-app-resolver` 负责固定版本 App 接口适配，`hongguo_app_input.py` 与 `hongguo_progressive.py` 负责媒体输入及按需处理。`src/runtime.rs` 和发布脚本负责开发环境与安装目录的依赖定位。

## 踩坑与经验

1. **媒体不兼容不等于播放器不适合。** libmpv 早期出现尺寸、时钟和 codec 状态，却实际花屏；内部截图与 WGC 都确认了错误画面。所测输入是原始保护分轨，不能据此否定引擎，错误解码的低 CPU 也不能算性能优势。后来按实际 currentSrc 取得的兼容流可由原生方案正确播放，进一步说明取源与呈现需要分开判断。
2. **清晰度问题先追输入。** 最初 360p 来自官网兼容回退，并非 Iced/GStreamer 的分辨率上限。720p 接口元数据正常仍不足以播放，还要确认保护封装、视频/音频轨及真实解码尺寸；网页双轨 fMP4 与 App 单文件 MP4 的处理方式不能直接互换。最终只交付已验证的档位，不把某次 1080p 请求失败推广为全站结论。
3. **登录、目录和观看权限是独立能力。** 已登录或拿到完整目录，仍不能证明每集可播放。网页可见集数与 App 目录不同，接入过程分别核对分集标识、会话、设备及媒体响应；代表性中后段的取址、音视频和跳转通过，仍不代表任意账号、任意剧集或全集权限。
4. **先拆耗时，再改架构。** 旧链路包含浏览器准备和整集双轨下载。通过分阶段测量，最终保留已验收的 Iced/GStreamer，仅替换为 App 取源与有界 Range 输入，复用同账号的内存设备档案及目录。标准 GstProtectionMeta 路径在所测输入未通过后，才验证样本索引适配；没有用下一集预加载掩盖首次等待。短次观测中首帧、切集明显改善，但输入编码/码率不同，不计算通用性能倍数。
5. **界面状态不能冒充媒体状态。** 拖动进度需要区分预览、期望位置和实际 PTS；普通倍速与临时加速共用保音高链路；自动连播依赖真实 EOS。缩放期间工作线程已完成、UI 尚未处理消息，曾被误判为加载超时，说明完成时间不能只看 UI 收到消息的时间。悬停控件和菜单保持显示不能改变视频尺寸或重建管线。
6. **异步反馈与最终确认分开。** 收藏采用乐观星标，失败撤销本地覆盖，服务端结果仍需读回；取消请求不能承诺服务端回滚。观看进度按更新时间合并，较小集号也可能是较新的重看。暂停、隐藏、切页和静音需要独立建模，最终约定为隐藏保留暂停管线，离页释放，静音仅由用户选择。
7. **后台操作也需要证据边界。** 业务 CLI、真实 Iced 控件事件、renderer、遮挡 WGC 和隔离系统输入验证不同层次。旧 revision、菜单不可见项和换集后控件隐藏曾导致验证被正确拒绝，不能为让脚本通过而放宽保护。音频 PTS 不替代听感，接口读回不替代手机 App 刷新，后台 resize 不替代真实系统拖拽；测试窗口不抢焦点，也不读取整个工作桌面。
8. **开发机能运行不等于安装包可交付。** 正式分发需要 GStreamer DLL/插件、MSVC 运行库、私有 Python、账号/媒体/封面辅助及许可，并脱离开发机 PATH 验证。1.0.0 构建失败暴露出 MSI 下载与 TARGETDIR 重合的问题，本地原布局复现 1603/2203；此前已有 SDK marker，检查跳过了首次解包。分离目录后，Runtime/Development 在空目录及含空格路径均成功，增加日志留存，并由 1.0.1 接替失败发布，未改写既有标签。

## 逐集能力与失败恢复

同一部剧的编码能力也会逐集变化：本轮指定剧220/221集的360–720p使用ByteVC2，1080p才提供标准HEVC；222集有四档兼容源。固定档位查找会把“存在720p”误当成“播放器支持该720p”。逐集读取模型，按清晰度与编码联合选择，材料必须与选中的表示绑定；同档不兼容时优先更高的兼容源，保持实际分辨率可见。未出现兼容源时明确失败，不能把模型可见或账号登录等同于能播放所有编码。

失败恢复是播放器能力的一部分：解码失败不应让目录和当前选集消失，也不能把“重试当前集”转成“重新按历史打开”。本轮把播放成功、视图打开、可选目录拆开判断，并用人为失败验证Iced上一集/选集和重试。后台长菜单还暴露出控件检查未应用滚动偏移的问题，修复可见坐标后再验收，而非关闭边缘保护。完整证据及首播分段见[player-startup-performance.md](player-startup-performance.md)。

## 可复用的推进顺序

先用最小隔离原型验证账号/输入、真实音视频、跳转、透明及静默，再确定取源与播放器组合；接入正式页面时复用业务状态机和 CLI；最后在干净依赖目录与独立打包目录验证交付。比较候选时先统一媒体并确认画面正确，发现瓶颈后只修改负责该瓶颈的层。

## 保留的验证边界

代表性720p及新增220/221集1080p的短时音视频观测不能外推全剧、其他1080p内容、长期同步、扬声器听感或资源优势；Windows 原生播放不能外推 macOS 功能对等。首次扫码新会话、手机 App 展示和安装升级等人工验收，以 TASKS.md 的对应记录为准。历史原型及阶段数字只解释当时决策，不作为后续默认行为。
